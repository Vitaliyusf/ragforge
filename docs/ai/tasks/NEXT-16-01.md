# NEXT-16-01 — Next.js 16 application navigation and rendering architecture

**Branch:** `perf/next16-app-architecture`  
**Phase:** Frontend / Product Track  
**Priority:** P1  
**Depends on:** `REACT-19-01`

## Goal

Use Next.js 16.3 routing/rendering capabilities to make RagForge behave like a persistent application workspace rather than a collection of remounting pages/tabs.

Target:

```text
persistent application shell
fast route transitions
stable structure available immediately
dynamic/live content streamed locally
smaller loading replacement areas
correct live-vs-cache semantics
preserved local UI state where valuable
```

This is an architecture task, not the final product/navigation redesign.

## Architecture target

Prefer:

```text
AppShell
├── persistent navigation/header
├── stable workspace frame
└── route-owned content
     ├── immediate/static shell
     └── local dynamic/live boundaries
```

Avoid:

```text
navigate
→ destroy providers/shell
→ recreate application chrome
→ reload unrelated data
→ restore local state manually
```

## Part A — Instant navigation

Audit:

- workspace navigation
- chat-thread navigation
- dashboard/settings transitions
- links blocked on route data
- unnecessary remounts

Use current Next.js 16 navigation/prefetch capabilities where they improve route transitions without caching live truth.

Measure where practical:

- route-transition latency
- shell availability
- remount count
- loading-state duration
- client JS impact

## Part B — Partial prefetching

Identify reusable route-shell content that can be prefetched independently from dynamic route content.

Good candidates:

```text
navigation structure
workspace chrome
stable headers
static help/config descriptions
stable route metadata
```

Do not prefetch/cache expensive live streams merely because the framework allows it.

## Part C — Cache Components / cache boundaries

Start with the negative question: where is caching forbidden?

### LIVE_OPERATIONAL_TRUTH

Examples:

```text
Logs
Health
active ingestion
streaming Chat output
active Eval runs
runtime model health/status
```

These remain dynamic/live unless current source proves a safe bounded stale policy.

### STABLE_CACHEABLE

Examples:

```text
application shell structure
static help text
stable settings descriptions
navigation metadata
stable labels/config schema
immutable historical fragments where proven safe
```

Rule:

> Cache static structure; never accidentally cache operational truth.

Before accepting any cache:

```text
owner known?
data mutability known?
staleness tolerance known?
invalidation known?
tenant/user scope preserved?
```

If any answer is unclear:

```text
DO NOT CACHE
```

## Part D — Suspense/loading architecture

Prefer:

```text
stable shell
+
small local loading boundary
+
streamed dynamic content
```

over full-screen replacement.

Target:

- less layout replacement
- lower perceived latency
- lower CLS
- less state loss

Do not create dozens of tiny Suspense boundaries without product value.

## Part E — React `<Activity>`

This task owns broad evaluation/adoption of `<Activity>` because its value depends on route/workspace lifecycle.

Candidate surfaces:

```text
Metrics
Logs
Files
Eval
drawers
secondary workspace panels
```

Use when preserving local UI state is valuable:

```text
filters
scroll position
draft forms
panel state
selection
```

Evaluate memory/runtime cost.

Do not wrap every tab.

For each adopted surface document:

```text
state-preservation value
effect lifecycle behavior
memory/runtime cost
why mount/unmount is worse
```

## Part F — Provider/remount cleanup

Audit whether route changes unnecessarily recreate:

- auth/session providers
- theme
- socket clients
- application state
- workspace chrome

Move stable ownership upward only where it removes real remount/reconnect behavior.

Do not create a giant global provider tree.
