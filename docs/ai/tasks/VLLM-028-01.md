# VLLM-028-01 — Upgrade to vLLM 0.28.0 safely and establish the next scheduler-tuning baseline

**Status:** completed / historical — retained as execution evidence. Runtime/tooling text here is superseded by `docs/ai/RUNTIME_CONTRACT.md`.

**Branch:** `perf/vllm-028-upgrade`

## Goal

Evaluate whether moving RAGForge from:

```text
vllm/vllm-openai:v0.27.1
```

to:

```text
vllm/vllm-openai:v0.28.0
```

is a safe and worthwhile direction **before** changing scheduler tuning.

This task is intentionally staged:

1. establish a trustworthy post-GEN-03B `0.27.1` control;
2. upgrade only the vLLM image to `0.28.0`;
3. keep Model Runner V2 disabled on WSL2;
4. keep all existing production tuning fixed;
5. add enough vLLM observability/provenance to know what the new scheduler is actually doing;
6. run a controlled Smoke30 comparison;
7. if the upgrade is healthy, produce the exact next tuning matrix for:
   - `max_num_batched_tokens`
   - `performance_mode`
   - optionally `gpu_memory_utilization`

Do **not** mix the version upgrade with new scheduler tuning in the first comparison.

# Why 0.28.0 is worth evaluating

vLLM 0.28 exposes / improves scheduler and runtime controls directly relevant to this workload, including:

```text
max_num_batched_tokens
max_num_scheduled_tokens
performance_mode
async_scheduling
chunked_prefill
stream_interval
scheduler_reserve_full_isl
```

`performance_mode` supports:

```text
balanced
interactivity
throughput
```

The important future tuning candidate for this workload is:

```text
max_num_batched_tokens
```

because RAGForge has relatively large prefills compared with short answer generations.

However, first determine whether the version upgrade itself is neutral or beneficial.

# PART 14 — Performance decision thresholds

Use these as decision rules, not as claims of statistical significance.

## Clear win

If 0.28 is:

```text
>= 10% faster wall time
```

with no reliability or quality regression:

```text
KEEP 0.28
```

and proceed to tuning.

## Near-noise region

If the difference is:

```text
within ±5%
```

treat the version-only performance difference as approximately neutral.

Keep 0.28 only if:

```text
runtime/reliability remains clean
and
the new tuning/observability capabilities justify the upgrade
```

## Ambiguous

If difference is approximately:

```text
5–10%
```

in either direction:

repeat:

```text
0.27.1 control
0.28.0 candidate
```

once each.

Compare medians / consistent direction.

## Clear regression

If 0.28 is repeatedly:

```text
>10% slower
```

or introduces:

```text
OOM
provider errors
structured-output regressions
startup instability
incorrect streamed usage
```

then:

```text
ROLL BACK to 0.27.1
```

and stop this tuning direction until the cause is identified.

Do not reject an otherwise healthy runtime based on one stochastic quality fluctuation.

Inspect:

```text
groundedness
citation precision
citation recall

```

A quality regression is credible when supported by:

```text
repeated direction
or
specific deterministic malformed/truncated outputs
or
new structured-output/provider failures
```

Do not explain stochastic variation as a version regression without evidence.

# PART 16 — If 0.28 passes, prepare the first tuning sweep

Do not execute this sweep until the upgrade-only gate passes.

The next experiment should be:

## VLLM-TUNE-01 — `max_num_batched_tokens`

Fixed:

```text
vLLM=0.28.0
Model Runner=V1
performance_mode=balanced
max_num_seqs=4
gpu_memory_utilization=0.80
prefetch=4
same model
same token budgets
```

Candidates:

```text
4096
8192
16384
```

Also preserve the 0.28 upgrade-only run with the automatic/unset value as the reference.

Reason:

The workload has relatively large prefills and short generations, so scheduler token capacity is a plausible throughput lever.

Chunked prefill should allow requests larger than the per-iteration token budget to be processed in chunks when supported.

Do not assume `16384` is better merely because it is larger.

Choose the smallest value that provides a material wall-time/throughput benefit without worsening:

```text
TTFT
ITL
tail latency
KV-cache pressure
preemptions
reliability
```

# PART 17 — Second tuning sweep after batched-token winner

Only after choosing `max_num_batched_tokens`, test:

## `performance_mode`

Candidates:

```text
balanced
throughput
```

Keep explicit:

```text
max_num_seqs=4
max_num_batched_tokens=<winner>
```

This is important because `throughput` mode can otherwise modify automatic scheduler defaults.

We want to measure the runtime/kernel/CUDA-graph policy difference, not accidentally change multiple independent knobs.

Do not test `interactivity` as the primary benchmark candidate.

Use `interactivity` only later if Chat TTFT/streaming UX becomes a separate optimization target.

# PART 18 — Conditional GPU-memory sweep

Current:

```text
gpu_memory_utilization=0.80
```

vLLM 0.28 permits higher allocation, but do not increase it automatically.

Use the new vLLM metrics first.

If at `0.80` the benchmark shows:

```text
high KV-cache pressure
preemption/recompute
waiting caused by KV capacity
```

then test:

```text
0.85
0.90
```

If KV cache has comfortable headroom and no preemption:

```text
SKIP this sweep
```

because additional reserved memory is unlikely to be the current bottleneck.

Never choose a value that causes intermittent OOM or harms desktop/system stability.
